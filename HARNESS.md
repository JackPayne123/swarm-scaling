# Harness

One harness for every task family: Inspect AI + inspect_harbor for tasks, sandboxes and scoring, plus a custom multi-agent solver (to build) passed via `--solver` / `solver=`. Facts below were checked in source and against the live Harbor hub on 2026-10-05 unless marked as inference; nothing has been run with a model yet.

## Why this stack

- inspect_harbor (Meridian Labs, 1.0.0+, last commit 2026-10-01) runs Harbor datasets as Inspect tasks. Registry: https://meridianlabs-ai.github.io/inspect_harbor/ and https://inspect.aisi.org.uk/evals/. Entries: `inspect_harbor/algotune` (154), `inspect_harbor/harveyai_lab` (1,251), `inspect_harbor/bencalvert04_programbench` (200), `inspect_harbor/yanagiorigami_frontier_cs` (172), plus `inspect_evals/frontier_cs` (238).
- Custom solver: `inspect eval inspect_harbor/algotune --solver path/to/swarm.py@swarm`. Default agent is react() with bash(timeout=300), python(timeout=300), update_plan and CompactionEdit.
- Scoring: `harbor_scorer` copies `/tests` into the same container after the solver returns, runs `test.sh`, reads `reward.txt` / `reward.json`, then deletes `/tests` and `/logs/verifier`. Score.value = reward; `passed = reward > 0`; the built-in metric is the arithmetic mean.
- inspect_harbor does not enforce Harbor's agent timeouts. Set Inspect time and token limits ourselves.

## Nothing off the shelf does what we need (survey 2026-10-05)

- Inspect 0.3.276: no peer, team or messaging primitive. `deepagent(background=True)` is orchestrator-style (information flows subagent to parent only). Per-agent models work (react(model=...), get_model). Limits are a ContextVar tree: concurrent agents each inside their own `token_limit` / `run(limits=...)` get independent budgets, usage rolls up to any sample-level limit, overshoot at most one call. Uncaught errors in a `collect()` task cancel siblings, so wrap each agent.
- inspect-swe 0.2.71: Claude Code agent teams do not spawn in `-p` mode (inspect-swe's mode), and are lead-spawned and dynamic anyway. Codex Multi-Agent V2 runs through the bridge, but it is OpenAI-only, root-led, has no per-agent token limit, and message payloads are encrypted (cannot log contents). Usable only as an OpenAI-only side check on a different scaffold.
- Park et al. released code (github.com/jerryjonghopark/test-time-communication, 2026-10-04): a Harbor agent running k Copilot CLI processes with shared logs and a score board, no message injection, one model per run, budget by timeout. Does not plug into inspect_harbor 1.0 (which dropped the harbor dependency). Reuse its prompts and anti-herding protocol ideas, not the code.
- DeLM (github.com/yuzhenmao/DeLM): Codex / Claude Code CLIs, separate containers, not Inspect, not mixed.
- Anthropic large-team harness: spec only (Opus 5.5 card s8.12.4: Send Message "inserted following the recipient's next tool result"; Wait for Message "blocks sampling"). No release found.
- Frameworks (OpenAI Agents SDK, langgraph-swarm, AG2, CAMEL, MetaGPT): handoff or coordinator patterns; none gives flat concurrent peers with injection, hard per-agent budgets and sandbox tools. Wrapping one adds a layer and still needs the same custom code.
- Harbor 0.24.0: one agent per trial (plus an optional simulated user). No multi-agent trials.

Decision: build a thin custom Inspect solver. Estimate 300-500 lines plus 150-250 lines of mockllm tests (estimate, not measured).

## Solver design

Implemented in `src/swarm_scaling/swarm.py` (solver, prompt, cleanup) and `team.py` (inboxes, registry, tools); tests in `tests/test_swarm.py`, wiring check in `scripts/smoke_swarm.py`.

```
swarm(models: list[str], per_agent_tokens: int, messaging=True, registry=True,
      workspace_root="/app", setup: Solver | None = None,
      finalize: Callable[[TaskState, list[Candidate]], Awaitable[None]] | None = None,
      protocol_prompt: str | None = None, reasoning_effort: dict[str, str] | None = None,
      time_limit: int | None = None, reveal_model_family=False, budget_type="all",
      candidate_file: str | None = None)
```

- Each agent = inspect_harbor's default react() scaffold (bash, python, update_plan, CompactionEdit) with its own model. N = 1, independent and team arms therefore share the scaffold by construction. Mixed teams = a different model per agent.
- Concurrency: `collect()` over N agents, each inside `run(agent, limits=[token_limit(per_agent_tokens)] (+ time_limit))`, each wrapped so one failure does not cancel the others. Budget unit: `budget_type`, below.
- Dollar budget (2026-10-09, harness-v4): `budget_type="cost"` (the runner default, `--budget 5` = $5 per agent) runs each agent inside Inspect's `cost_limit`; since 2026-10-11 (haiku branch) the swarm meters every call into it itself (`swarm.MeteredModel`), from the provider-reported usage, with `swarm_scaling.prices.usage_cost`, the function `scripts/run_cost.py` prices each logged call with: fresh input at the input price, cache writes at 1.25x input (2x for the 1-hour TTL), cache reads at the model's own multiple of input (Anthropic's pricing page, 2026-10-09: 0.05x for Opus 5.5 and Sonnet 5.5, 0.025x for Fable 5.1, 0.1x for every other model in the table), output (incl. reasoning) at the output price. A model with a long-prompt rate card (`prices.LONG_PROMPT`; Haiku 5.5: $0.10/$0.50 up to 100,000 prompt tokens, $0.50/$2.50 above, prompt = input + cache read + cache write) is priced per call at the tier that call's prompt selects; Inspect prices a model with one flat `ModelCost`, which cannot express that, so Inspect is given no price for agent models (a model Inspect prices itself is refused, as its calls would count twice). Inspect's usage records have no TTL split of cache writes, so the live meter prices a write by the TTL Inspect sent the request with: 5 minutes, or 1 hour once Inspect has switched the sample after a gap of over 5 minutes. Without server tools that is the TTL Anthropic reports in `usage.cache_creation`. `scripts/run_cost.py` prices each model event of a log the same way (every write of a pinned model as 1-hour, otherwise only where a logged raw response reports it), checks the per-call sums against the log's per-model totals, and reports long-prompt calls and their dollars. A model with no single match in the table is refused before any sandbox starts. Checked on pilot 5 logs: per-call and the earlier per-model pricing give identical totals for Opus 5.5. Each agent also runs an uncapped `token_limit`, so token counts are logged as before; `tokens.metered` is then dollars. check_budget, the warnings and the prompt speak dollars ("You have a budget of $5.00, counting every model call at its API price: ..."). Token budgets (`"all"`, `"output"`) still work (runner `--budget-type all`). The runner refuses a cost budget above $100 per agent (`MAX_COST_PER_AGENT`), so a token-sized `--budget` passed without `--budget-type all` cannot run as dollars; `scripts/pilot1-3*.sh` pass `--budget-type all` explicitly.
- Prompt-cache TTL (2026-10-10): every call of an `anthropic/` agent model pins the 1-hour TTL (`swarm(anthropic_cache_ttl="1h")`, the default, through Inspect's anthropic `cache_ttl` model arg; `None` restores Inspect's default). Inspect's default ("auto") sends the 5-minute TTL until the sample has gone more than 5 minutes without calling that model, and its gap clock is per sample and model, so teammates' calls keep resetting it; in pilot 4, 9 calls of the team of 4 after dev_eval waits of 158-421 s rewrote the whole cache (`scripts/run_telemetry.py`). Each request now carries `"cache_control": {"type": "ephemeral", "ttl": "1h"}` at the top level and on the last tool (captured with a fake transport in `tests/test_runner.py`), and Inspect's cost, so the dollar budget, prices those writes at 2x input. Logged as `state.metadata["swarm"]["anthropic_cache_ttl"]` and per agent `cache_ttl`; `scripts/run_cost.py` counts every write of a pinned model as 1-hour.
- Messaging tools: `send_message(to, text)` with `to` = agent id or `all`; `wait_for_message(timeout_s)`, at most 600 s per call (`team.WAIT_MAX_S`, stated in the tool description; 2026-10-10, so an agent under run-to-budget cannot idle until its 16 h time limit). Per-sample in-memory inboxes. A message to a finished agent is dropped and the sender is told. Finish notices (2026-10-09, harness-v4, messaging arms only): when an agent ends, every teammate still running gets "agent_k has finished (submitted | budget used | time limit | stopped) and will not read further messages." through the normal channel, from sender `system` (logged in `messages_received` with `"from": "system"`, so subtract these when counting peer messages); it also ends a waiting teammate's `wait_for_message`. Agents that have already finished get none. `wait_for_message` returns at once when every teammate has finished or is also waiting, so the team cannot deadlock. Deliveries are capped (2026-10-08): each message shows a 2,000-character preview, a delivery stops listing bodies after 8,000 characters (the rest appear as id/sender/length headers), and `read_message(id)` returns a full text; logs keep full texts. Prevents a team of 8 from flooding every context. Direct file sharing (pilot 2, 2026-10-08): `send_file(to, path, note)` copies any file or folder into each recipient's `<workspace>/agents/<id>/inbox/from-<sender>-<k>/` (the recipient's own writable copy; below the working directory, so not a selection candidate) and messages them the location. The prompt also states that teammates' working directories are readable.
- Delivery: wrap every tool so pending peer messages are appended to the tool result (Anthropic's documented delivery point). This keeps react()'s compaction; the alternative (react(model=<custom Agent>)) disables compaction. Envelope per message: sender id, sender model id (only with `reveal_model_family=True`), UTC timestamp, payload, rendered as a text block after the tool output.
- Budget warnings (2026-10-08, every arm, on by default): `budget_warnings=(0.5, 0.75, 0.9)`; `()` disables. Every agent tool is wrapped outermost (so message tools and deliveries too); after a tool result, if the agent's own `token_limit` usage has passed a threshold not yet announced, `[budget] You have used 75% of your token budget (1,503,211 of 2,000,000).` (dollar budget: `... of your budget ($3.76 of $5.00).`) is appended. Each threshold once; if several are passed at once only the highest is shown and the lower ones count as done. Logged per agent as `budget_notices` (`threshold`, `used`, `at`). The prompt states that notices appear. Reason: in the pilot an agent ran out of its 2M budget mid-work without saving a solution and never called `check_budget`.
- Run to budget (2026-10-10, harness-v5; PLAN.md decisions log): `swarm(min_spend_frac=...)`, runner `--min-spend-frac` (default 0.8; 0 restores free stopping), applies to every arm and every agent on its own budget. Until the agent has used that fraction of its own budget, `submit` raises a ToolError, so the agent keeps running; react() treats any submit result without an error as the final answer, so the refusal has to be a tool error. Its text states spent, remaining and the threshold: "submit refused: you have used $1.20 of your $5.00 budget ($3.80 remaining). submit is accepted once you have used 80% ($4.00). Your run ends when your budget is used up, when the time limit is reached, or when you submit after that point." The prompt's budget sentence says the same ("submit is refused until you have used 80% of your budget ($4.00). Your run ends when your budget is used up, when a wall-clock time limit is reached, or when you submit after that point."), replacing "You may stop at any time by submitting; you do not have to use the whole budget"; check_budget's description changes the same way. The time limit's value is not stated to agents (as before). An agent that answers without a tool call is continued by react()'s own continue prompt ("Please proceed to the next step ... call the `submit()` tool"), which then meets the refusal; react() only ends early on an unhandled context overflow or three consecutive content-filter stops (end reason `stopped`). When the budget is spent the agent ends as before and finalize picks the best candidate (AlgoTune's protocol). Logged: `state.metadata["swarm"]["min_spend_frac"]`, runner metadata `min_spend_frac`, per agent `submit_refusals` (`used`, `at`) and `end_reason` (`cost` or `token` = budget, `time`, `submitted`, `stopped`, `error`). Test: `test_submit_is_refused_below_the_spend_threshold_and_the_agent_keeps_running`; mock end-to-end with a local scorer (2026-10-10): a scripted agent's submit at $0.012 of $0.10 was refused, a no-tool turn was continued, and the run ended by budget at $0.113 (`end_reason` cost), then finalize and scoring ran on the scorer.
- Tool style (2026-10-08): `tool_style="claude_code"` (runner `--tool-style claude_code`, recorded in run metadata and `state.metadata["swarm"]["tool_style"]`) tests whether Claude coordinates better with tools shaped like Claude Code's agent-team tools. Team arms only: `SendMessage(to, message, summary)` replaces `send_message` (same delivery, truncation and `all` broadcast); deliveries render as `<teammate-message teammate_id="agent_0" summary="..." message_id="m0">...</teammate-message>` (`read_message` keeps its name); and a shared task list: `TaskCreate(subject, description)`, `TaskList()`, `TaskGet(taskId)`, `TaskUpdate(taskId, status, owner)` with status pending / in_progress / completed, any agent may update any task, events logged in `state.metadata["swarm"]["tasks"]`. Every other tool and the solo/independent arms are identical in both styles; the prompt describes the tools in the same facts-only register.
- Registry: `publish_candidate(path, note)` copies the file or directory into `{workspace_root}/registry/agent_{i}-{k}` and makes it read-only (`chmod -R a-w`); `list_candidates()`. With `candidate_file` set (runner: `solver.py`) a published single file is saved under that name and the tool result says so; in pilot 3, 13 of 23 team publishes were files like `v5.py` that finalize rejected as "no solver.py". Directory publishes are copied as before. Private dirs `{workspace_root}/agents/agent_{i}`. Default root `/app` because Harbor tasks score there.
- Independent arm: separate N = 1 samples with `messaging=False, registry=True` (private saved candidates, same pick-pool mechanism as teams), resampled into teams afterwards. `swarm()` refuses N > 1 with messaging and registry both off, because agents in one container share a filesystem and would not be independent.
- No lead. Same protocol text appended to the task instruction for all agents, naming teammates by id (decide before freezing whether to reveal model family in the mixed arm: `reveal_model_family`).
- `setup` runs once before the agents start (AlgoTune dev toolkit install). `agent_tools(state)` adds task-specific tools to every agent in every arm (AlgoTune: `dev_eval`). `finalize(state, candidates)` runs after they end and writes the task's single deliverable: AlgoTune selector evaluates every candidate in the checker container (below), removes any agent-written `/app/solver.py` and copies the fastest correct candidate (on dev inputs) to `/app/solver.py`; the prompt states this (`final_path`), so agents know that writing `/app/solver.py` themselves has no effect; Harvey merge step writes the named `.docx` files. Both run in every arm, and the Harvey merge cost counts against the budget. `candidates` = every registry entry plus each agent's final private dir (`kind` = `published` / `final_workspace`).
- Before finalize: kill every process in the container (scoring ran in the same container and is timing-sensitive for AlgoTune; since 2026-10-09 AlgoTune scores in its checker container instead). Container-only, by two positive checks: the environment behind Inspect's `SandboxEnvironmentProxy` must be a `DockerSandboxEnvironment`, and a probe inside the sandbox must confirm Linux + `/.dockerenv` + `/proc` with PID 1 not launchd. Before agents start, the same checks gate a snapshot of the container's PIDs; the kill script walks `/proc` and SIGKILLs every PID not in that baseline except 1, itself and its ancestors. The baseline is required: the first real-container test (2026-10-05) killed the container's keepalive (PID 1 is an init whose child keeps the container up) and the sample errored before scoring. On any other sandbox nothing is executed (`state.metadata["swarm"]["process_cleanup"]` records what happened). Verified in a real AlgoTune container with `scripts/check_cleanup_in_docker.py`: an agent-left `sleep 600` was killed (`killed 1`), the container survived and the sample scored, and the host was untouched.
- Logging per agent (one agent span each via `run(name=agent_id)`) in `state.metadata["swarm"]["agents"]`: tokens by type from `Limit.usage`, which limit hit, end reason, messages sent/received/dropped with contents, candidates published, candidates read (list_candidates calls plus registry paths seen in tool arguments), start/end wall-clock.
- Set `reasoning_effort` explicitly per model (Inspect issue #4295: unset defaults differ across providers). `--reasoning-effort xhigh` reaches Anthropic for claude-opus-5-5 as `output_config: {"effort": "xhigh"}` with `thinking: {"type": "adaptive"}` and max_tokens 64,000 (Inspect 0.3.276 maps xhigh for every Claude 4.7-or-later model, which includes Claude 5; its docstring saying "4.7 only" is stale). Captured from the request body with a fake HTTP transport in `tests/test_runner.py`; no live call.

### Hard parts

1. Termination and deadlock: all agents blocked in `wait_for_message`; messages to finished agents; one agent out of budget while peers continue.
2. Token accounting parity across arms and providers. Inspect's `all` counts cached input on every request; the Opus 5.5 card counts each token once per context window. Pick one definition and apply it to every arm; messages are charged to the recipient.
3. Shared-sandbox CPU contention for timing-based scoring.
4. Provider quirks: GLM tool-call formatting, `max_connections` with N agents x concurrent samples.
5. Attributing interleaved events (span per agent).

## Per-family setup

### AlgoTune (`inspect_harbor/algotune`, hub copy published 2026-03-21)

- Agent sees an empty `/app`. Instruction pastes the reference `solve` and `is_solution` as bare methods (helpers and imports stripped). No `generate_problem`, no eval command (the adapter's "use python test_outputs.py" line is absent from the hub copy). `/tests` (evaluator, generator) only appears at scoring.
- Fix: before agents start, install a dev toolkit in `/app/dev/`: the task's `generate_problem`, `is_solution`, reference solver and a timing script. Same toolkit in every arm. This restores the original AlgoTuner eval command.
- Checker container (2026-10-08): in a 4-agent pilot run one agent's 14-process background job inflated every agent's `dev_eval.py` timings, and agents acted on those numbers. Each sample now has a second compose service, `checker` (`tasks.add_checker`): the same image, no network, not reachable by the agents' bash/python tools. The agent box is pinned to cpuset 0-7 and the checker to 8-15 of Docker's 16 CPUs, so the checker times on 8 CPUs (since harness-v4 the agent box size follows the team size; see CPUs and memory below). `dev_eval.py` and `config.json` live only in the checker; the agent box keeps `reference_task.py` and `README.md`. Every agent in every arm gets a `dev_eval(path, n=20, seed=0, reps=10, size=None)` tool that copies that one file into a fresh checker directory as `solver.py`, runs `dev_eval.py` there (900 s timeout, enforced by `timeout` inside the container, run shielded from cancellation) and returns its report with the queue wait. Calls are serialised by one FIFO lock (`CHECKER_LOCK`), shared since 2026-10-09 by every sample in the process and by final selection and scoring, so the queue wait includes other samples' work; each is logged in `state.metadata["checker"]["calls"]` (agent, start, queue wait, run time, valid, speedup, error), summarised by `scripts/analyse_team_run.py`. Final selection runs in the checker too, each candidate evaluation holding the lock (queue wait and start/end in `state.metadata["finalize"]["candidates"]`). The compose config goes to Inspect as a generated file in gitignored `data/.algotune_compose/` (YAML also in sample metadata `compose_yaml`), because Inspect re-validates inline configs when reading logs and rejects `cpuset`.
- `task.toml` (identical for all 154): cpus 8, memory 16 GB, agent and verifier timeout 3600 s, network public. Turn agent network off (agents could fetch the AlgoTune repo with every generator). The verifier does not need network.
- Seeds (2026-10-05): the hub verifier builds its 100 instances with `random_seed=i` for i in 0..99, and agents hold `generate_problem`, so `algotune_task` runs a patched copy of `tests/` (`seed_with_offset`, pure function) that uses `ALGOTUNE_SEED_OFFSET + i`. One offset serves the whole experiment, so every arm and repeat is scored on the same instances: it is generated once (1,000,000 to 2^31-1000, disjoint from dev seeds 10,000+ and selection seeds 60,000+) into the gitignored `data/.algotune_seed_offset` and reused; exporting `ALGOTUNE_SEED_OFFSET` overrides it. If the file is lost it is restored from the offset recorded in `logs/*.eval` (several different offsets there raise instead); creation is atomic. Pre-experiment dev logs live in `logs/dev-2026-10-05/` so their trial offsets are not read. Hardening (2026-10-05): the offset is not in the verifier's environment; it travels as a `seed_offset` file in the scoring-time /tests copy (built in gitignored `data/.algotune_verifier/`), which the verifier reads and deletes while generating problems, and the fixture order is swapped so problems are generated before the solver is imported. A solver could still find the generated problems in process memory during timing; the exploit audit covers that. The hub dataset is pinned to `sha256:69d264f1...` (ALGOTUNE_REF); it reaches the container only as scoring-time `verifier_env` and is recorded in the eval header (`eval.metadata["algotune_seed_offset"]`) and each sample's `verifier_env`. The image, protocol and problem size are unchanged. A solver that reads `/tests` or its environment while it is being scored can still see the offset.
- Reward = total baseline time / total solver time over 100 instances x 10 reps, interleaved, min taken; invalid or < 1.0 becomes 1.0; missing solver or constructor failure = 0. Compute our own metric (per-task log speedup, plus harmonic mean for comparability) from raw rewards; ignore the built-in mean and `passed`.
- CPUs and memory (2026-10-09, harness-v4, for one-sample-per-VM runs on GCP): every agent gets the same CPUs. `tasks.box_resources` gives the agent box `cpus_per_agent` x agents CPUs (runner `--cpus-per-agent`, default 4), pinned to cpuset 0..A-1, and the checker 8 CPUs pinned to A..A+7. The Docker host's CPU count and memory are read with `docker info` when the task is built (replacing the Mac's hard-coded 16 CPUs), and the build fails if A + 8 exceeds the CPU count (e.g. 4 agents x 4 CPUs on the Mac's 16). Agent box memory = (host memory - 8,192 MiB checker - 2,048 MiB headroom) / `--parallel`, no cap; the checker keeps 8 GB. `cpus_per_agent`, both CPU counts, cpusets and memory limits and the host's size go in the task metadata (`eval.metadata`). The agents in a box still share its CPUs; nothing pins an agent to its own.
- Checker cleanup (2026-10-09, harness-v4): a solver can leave a process running (a daemon, a forked child) into later timings, or into scoring, where it could read `/tests/seed_offset`. `algotune_setup` snapshots the checker's PIDs (`state.metadata["checker_baseline_pids"]`, its init and keepalive), and before every timed checker run (each dev_eval call, each finalize evaluation, final scoring), holding `CHECKER_LOCK`, `end_checker_processes` kills every checker process not in that snapshot. It is the agent box's guarded kill (`kill_agent_processes(baseline, "checker")`): nothing runs unless the checker is a `DockerSandboxEnvironment` and the in-container probe passes. Each result is logged (`cleanup` in `checker.calls`, in finalize's candidates and in the score's `metadata["checker"]`). Not yet run in Docker: `scripts/smoke_harness_v4.py --part cleanup`.
- Reference check (2026-10-09, harness-v4; criterion replaced in round 5): the verifier and dev_eval time reference and solver interleaved in one process, so whatever a solver leaves running (spin-waiting threads, a busy pool) can slow the reference and inflate the speedup; in pilot 3 a solver with 4 spin-waiting threads scored 3837x on dev_eval. `algotune_assets/thread_guard.py` now measures the harm itself. `AloneTimer` starts a child process before the solver is imported; after each instance's interleaved timing the child generates the same instance and times the reference alone (one untimed and `reps`/`NUM_REPEATS` timed calls, minimum). Inside a container the two processes never run at once: the child SIGSTOPs the timed process while it times (and checks in /proc that it stopped, failing loudly otherwise: PID 1 of a namespace ignores SIGSTOP, so timed containers run with `--init`), and the timed process SIGSTOPs the child between requests, so neither the solver's leftovers nor either process's idle OpenBLAS pool (whose threads keep spinning for a while) competes with the other's timing. Alternating per instance cancels drift in machine speed. A run is invalid ("the reference ran 1.23x slower while timed with the solver: ...", scored 1.0) when the interleaved reference totals more than 1.15x the alone reference over the timed instances. `reference_inflation` is logged per dev_eval call, finalize candidate and score (verifier line "Reference inflation: <ratio>", local and scorer service). Solver-thread CPU (`thread_check`, /proc/self/task) is still logged but no longer decides validity. History: the first version invalidated on solver-thread CPU above 0.1 x reference time + 25 ms per call; it flagged two legitimate pilot-3 eigenvalue solvers whose `blas_thread_shutdown_` makes OpenBLAS restart its pool (reference time normal). A second version timed the reference alone once before the solver import; on a busy Mac machine-speed drift made legitimate dst solvers read 0.78x and 1.45x. Known limits: a child process the solver starts is not paused; the check is in-process and not adversarially robust. Results of the smoke run are in the round 5 report; the verifier copy gets the check from `tasks.with_thread_guard`.
- Scoring timeout (2026-10-09, harness-v4): `algotune_scorer` catches the `TimeoutError` Inspect raises when the verifier exceeds `verifier_timeout_sec` (3,600 s) and records Score 1.0 (no speedup, as an invalid run), explanation "verifier timeout after 3600 s", metadata `scoring_timeout` True (False otherwise), so one slow sample cannot fail the eval and lose the other samples' logs.
- First-call ratio (2026-10-09, harness-v4): the verifier checks only each instance's untimed first solver output, so a solver that caches results by problem identity would be slow once and near-free in the timed repeats. `tasks.with_first_call_ratio` makes our verifier copy record per instance the untimed first call and the min timed solver call and print "First-call ratio: <sum first / sum min-timed>"; `algotune_scorer` copies it to `metadata["first_call_ratio"]`, dev_eval writes the same `first_call_ratio` (logged per dev_eval call and finalize candidate, not printed to agents), and `scripts/rescore.py` flags rows above 5 for manual review. It never invalidates a run. Measured in the unit test: an honest sort solver about 2, a cache-by-`id(problem)` solver about 90,000. A solver that compiles or initialises lazily on its first call can also exceed 5.
- Remote scorer (2026-10-09, branch remote-scorer; spec `scorer-api.md`, kept with the cloud tooling): every timed run on dedicated slots of one machine type (planned: AWS c7a.8xlarge), so agent VMs on any cloud never time anything and never hold the seed offset. `src/swarm_scaling/scorer_service.py` (launcher `scripts/scorer_service.sh`, stdlib HTTP, default port 8770) seeds the verifier copies and dev_eval assets from the Harbor cache on startup (`tasks.seed_verifier`, the local code path), refuses to start without `SCORER_TOKEN` or the experiment's offset file, and serves `GET /health`, `POST /jobs` (kinds `dev_eval`, `final_eval`, `score`) and `GET /jobs/<id>` behind a bearer token. One FIFO queue for all callers; slot k (8 CPUs, `--first-cpu` + 8k) takes the next job. Each job is a fresh `docker run --rm` of the task image (no network, the slot's cpuset, 8 CPUs, 8 GB) with the solver and, for scoring, the seeded verifier piped in as a tar on stdin, so no process survives between jobs (this replaces the checker cleanup) and the offset file is never mounted. - Scorer noise (diagnosis 2026-10-18, v7b). In the v7 calibration (one c7a.8xlarge scorer with 3 slots, `logs/_scorer/i-0b09e81e911fb9ccd/jobs.jsonl`) the same source on the same hidden instances scored up to 1.16x apart. ode team agent_0-9 scored 190.85 at 19:08 on slot 1 and 164.53 at 21:29 on slot 0. The whole spread was in the solver's time. The reference timed alone in the same jobs varied by at most 1.3% between scorings of one source and 2.4% across all score jobs of a task (9.09-9.30 s on ode, 10.69-10.90 s on stable_matching), and machine type, CPU, slot count, timing environment and the alone measurement (`child`) were the same for every job. The sensitive solvers run 8 threads on about 0.5 ms per ode solve, synchronised at every step. stable_matching's picks varied by 1.01-1.02x, and in Phase B (11 busy slots of a c7a.24xlarge) 57 of 60 sources scored 3 or 6 times varied by at most 1.07x (generalized_eigenvalues_complex's reference 1.14x, sparse_lowest_eigenvalues_posdef's fast solver 1.39x). Over 18 ode scorings of 7 sources scored more than once, a scoring's solver time over its source's fastest averaged 1.075 on slot 0, 1.006 on slot 1 and 1.059 on slot 2, most of them with all three slots busy. The v7b smoke scorer (another c7a.8xlarge with 3 slots, `logs/_scorer/i-083d0b297a4e58bb7`; `analysis/v7b-smoke/measure_scorer.py` ran dev_eval n=20, reps 10 of the calibration's mixed-team pick and independents' pick) separated the parts. (a) Slot. Run alone, one at a time, the mixed pick took 11.04-11.39 ms on slot 1 and 10.20-10.78 ms on slots 0 and 2 (1.12x overall); the guest's L3 domains coincide with the slots (CPUs 0-7, 8-15, 16-23, 24-31), and slot 1 held containerd and an NVMe queue interrupt that the kernel does not let move. On the calibration VM slot 1 was the fastest, so the pattern differs between VMs. (b) Load. With all three slots busy the two picks ran 5% and 3% slower on average. (c) Drift. In rounds of exclusive jobs on slot 0 with nothing else running, all five sources were 3-7% slower in the second round than in the first. Moving dockerd, containerd, the latency holder and every movable interrupt to the service's CPUs (irqbalance stopped) left the slot difference in place (1.15x alone afterwards). The reference stayed within 1.8% throughout. Multi-threaded sub-millisecond solvers therefore carry per-VM slot effects, load and drift that the single-threaded reference does not, and so does any comparison scored across slots, loads or times. The fixes (`select_portfolio.py`, default for v7 logs) are these. Every hidden score of a selection comes from the scorer session it started on (one VM and machine type; the job's `session` is checked); hidden jobs are exclusive scorer jobs, run one at a time with the other slots idle on one fixed slot (`scorer_service --exclusive-slot`, default 0, because no slot was fastest on both VMs); they start once every pick is fixed, and a group's arms alternate repeat by repeat so drift falls on both. Pinning host processes (no effect measured) and more repeats per pick were not done. Hidden scoring is serial and holds the whole scorer. The smoke's unit_simplex_projection score jobs took 4.0 min each, so 5 hidden jobs per portfolio take about 20 min. The runs' own scores (finalize's pick, scored at the end of each run while other agents work) stay non-exclusive and are not comparison-grade.

- Grading (2026-10-05): `harvey_task()` (`src/swarm_scaling/harvey.py`) loads the tasks with `[environment] network_mode = "no-network"` (asserted per sample) and grades on the host with `harvey_grader` (`src/swarm_scaling/harvey_grader.py`): it reads `/workspace/output/red-flags-report.md` with `sandbox().read_file`, takes the criteria from the host's `tests/judge.toml`, and calls the judge through LiteLLM. Nothing from `tests/` enters the container (build context = `Dockerfile` + `documents/`, checked for all 11). Export the judge provider's key on the host (`ANTHROPIC_API_KEY`, or e.g. `GEMINI_API_KEY`).
- Judge: reproduces rewardkit 0.1.4 (Apache-2.0): prompt text, yes/no schema, score normalisation, `reasoning_effort="medium"`, 300 s per call, 1 MB file limit. Differences are listed in the module docstring; the main one is that the report comes before the criterion, so the instruction + report prefix is byte-identical across criteria and provider caching applies (Anthropic: `cache_control` on the report block; OpenAI and Gemini cache prefixes automatically). Request bodies were captured offline (no network): LiteLLM 1.104 sends Anthropic native structured output with adaptive thinking and the cache breakpoint intact, and Gemini `response_json_schema` with `thinkingLevel` medium. No live judge call has been made.
- Failures: each call gets 4 tries with 2/4/8 s backoff; a criterion that still fails scores non-pass and counts in `n_errored`. If every criterion errors (bad key, outage) the sample errors instead of scoring 0.
- Score: `Score.value` = `criterion_fraction` (errored = non-pass). Metadata: `all_pass`, `n_criteria`, `n_passed`, `n_errored`, per-criterion `{passed, reasoning[, error]}` (enough for the union-of-runs analysis without re-judging), `judge`, `batch_size`, `judge_usage` (calls, input / cached input / cache-write / output tokens, `cost_usd` from LiteLLM's price map, null if the model is unpriced). Metrics: `mean` (mean criterion_fraction) and `all_pass_rate`.
- `batch_size` (default 1 = Harvey's one call per criterion): k criteria per call with a fixed array schema of `{id, score, reasoning}`. rewardkit's batched schema keys on criterion names, so each call would compile a new grammar (Anthropic allows 20 per minute). Batching cuts calls and report re-reads k-fold, but criteria judged together can influence each other; compare against batch_size 1 before using it.
- Judge swap: `harvey_task(judge="gemini/<model>")` (any LiteLLM string). The default Claude judge is outside the cheap pair's families (GLM + Luna); for the frontier check (Sonnet 5.5 in the team) use a Gemini judge and validate it against the default on a few runs.
- Timeouts: `time_limit` (default 7,200 s, Harvey's agent timeout; inspect_harbor ignores task.toml's `[agent].timeout_sec`) is the sample limit, and Inspect caps scoring at half of it (3,600 s by default). `judge_timeout` is per call. The converter takes `--agent-timeout` / `--verifier-timeout`. None are measured.
- Parity check (not default): `harvey_task(rewardkit_parity=True)` adds Harvey's original in-container verifier as a second scorer and turns container network on, so use it only to grade a fixed deliverable, never for a scored agent run. That verifier (`tests/test.sh`) pip-installs `harbor-rewardkit[documents]==0.1.4`, runs `rewardkit /tests` (one call per criterion, no caching, one failed call aborts it and loses all results), then `tests/criterion_fraction.py` (source `scripts/harvey_criterion_fraction.py`) adds `criterion_fraction` to reward.json, which lands in `Score.metadata["reward_dict"]` (rewardkit's own key is `reward`, all-pass). It needs `ANTHROPIC_API_KEY` exported (a missing `[verifier.env]` var raises) and honours `REWARDKIT_JUDGE`. The in-container rewardkit installs whatever LiteLLM is current, so its provider mapping can differ from our pinned version.
- Harvey `task.toml` sets no CPU or memory; inspect_harbor leaves them unlimited unless overridden.
- The repo's native harness (`lab_core`) has no compaction (`context_overflow` aborts). Under Inspect the solo arm gets CompactionEdit plus a notes file.

## Known pitfalls

- Inspect retries rate-limit and quota errors with backoff for a long time by default, silently under `display="none"`. An exhausted OpenAI balance (`insufficient_quota`, seen 2026-10-05) looked like a hung run for 15 min. Set `max_retries` and `timeout` on every eval, and check provider balances before a grid.
- Inspect's OpenAI-compatible provider needs `openai>=3.1`; with an older version the eval fails before starting and `display="none"` hides the PrerequisiteError.

- Inspect's multi-agent docs warn that multi-agent designs "often don't out-perform simple react() agents". The solo arm is that baseline.
- Coordination is trained per lab on native tools; our custom tools may under-elicit collaboration. Validate message delivery and adoption in the pilot and limit conclusions to this harness. Optional side check: GPT-6.1 Sol via inspect-swe codex_cli Multi-Agent V2 (different scaffold, OpenAI-only, flag it as such).
- `multiagent-inspect` (Andon Labs) is stale and orchestrator-only. inspect_petri is single-target and only relevant to the addressee side project.
